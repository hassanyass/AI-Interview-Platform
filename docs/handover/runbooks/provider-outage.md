# Runbook — a provider is down or slow

Providers: **Groq** (LLM for both services; STT/TTS for the agent),
**LiveKit** (rooms, tokens, egress), **Supabase** (auth, resumes bucket,
possibly the database), **R2/S3** (recordings). Every backend call goes
through an adapter in `backend/backend/providers/` with a timeout and
bounded retries (H2-A); the agent's calls are bounded in
`agent/agent/interview/persistence.py`, `llm/groq_provider.py` and the
TTS/STT wrappers.

## Tell which one

```bash
curl -s localhost:8001/metrics | grep -E 'provider_call_failures_total|provider_call_duration_seconds_count'
```

`provider_call_failures_total{provider="groq",op="complete_json"}` rising →
Groq. `livekit` ops → LiveKit. `s3`/`supabase` → storage. Compare with the
`_count` to get a failure ratio. Then the log line for the failure
(`"level": "ERROR"` with the same `request_id` as the 5xx the user saw).

`/ready` returning 503 → the **database**, not a provider: see the log
line `Readiness: database check failed`.

## Effects by provider

| Provider down | Backend | Agent / candidate |
|---|---|---|
| Groq | question generation (admin) fails with an RFC7807 error carrying `request_id`; the final evaluation is generated by the **agent**, so a Groq outage at interview end leaves `final_result.evaluation_status = "FAILED"` — there is no automatic re-evaluation today (open item) | the interview stalls: LLM turns time out, TTS fails over across `GROQ_API_KEY_n` keys then the interview ends `DISCONNECTED`; STT loop restarts up to `STT_RESTART_MAX` |
| LiveKit | room creation / token minting fails → candidate cannot start; egress start retries `EGRESS_START_RETRY_ATTEMPTS` then the interview proceeds **unrecorded** (logged) | worker cannot register / rooms drop → sessions go `DISCONNECTED`, sweep finalizes them |
| Supabase auth | admin/candidate logins fail; existing JWTs keep working until expiry | none |
| Supabase storage | CV upload fails (`5xx`, user can retry) | none |
| R2 | recording upload fails at finalization (logged, session still finalizes) | none |
| Postgres | `/ready` 503, every API call 5xx | persistence retries then parks writes in the outbox and replays them in order; after `LEASE_ERROR_SHUTDOWN_AFTER` consecutive failed renewals the worker assumes the lease expired and leaves the room |

## Do

1. Confirm at the provider's status page; nothing in this stack fixes an
   upstream outage.
2. Do **not** restart services in a loop — retries and timeouts are already
   bounded; restarting the agent only kills live interviews.
3. If Groq is degraded for a long time: pause invitations (stop publishing
   new links) rather than letting candidates start interviews that will stall.
4. After recovery:
   - `make cli ARGS="finalize-stuck-sessions --dry-run"` → `runbooks/stuck-session.md`.
   - `make cli ARGS="backfill-evaluations --dry-run"` lists COMPLETED sessions whose legacy `final_result` evaluation has no `Evaluation` row yet.
   - Check `provider_call_failures_total` has stopped increasing.

## Swapping a provider

`LLM_PROVIDER`, `RECORDINGS_STORAGE_PROVIDER`, `RESUMES_STORAGE_PROVIDER`,
`REALTIME_PROVIDER`, `EMAIL_PROVIDER`, `NOTIFICATIONS_PROVIDER` select the
adapter; only one implementation exists for most today. Adding one:
`runbooks/add-provider-adapter.md`.
